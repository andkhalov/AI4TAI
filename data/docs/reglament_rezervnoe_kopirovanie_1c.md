# Регламент резервного копирования баз 1С

Документ учебный. ИТ-департамент, РГ-ИТ-07, версия 3.0 от 20.01.2026.

## 1. Объекты копирования

| База | Сервер | СУБД | Размер | Класс |
|---|---|---|---|---|
| УТ (Управление торговлей) | msk-app20 | MS SQL Server 2019 | 180 ГБ | критичная |
| ЗУП (Зарплата и управление персоналом) | msk-app20 | MS SQL Server 2019 | 40 ГБ | критичная |
| Бухгалтерия | msk-app21 | MS SQL Server 2019 | 65 ГБ | важная |
| Тестовая копия УТ | msk-test01 | MS SQL Server 2019 | 180 ГБ | не копируется |

## 2. Расписание

- Полная копия критичных баз: ежедневно в 01:00.
- Копия журнала транзакций критичных баз: каждые 30 минут с 07:00 до 22:00.
- Полная копия важных баз: ежедневно в 02:30.
- Копия конфигурации (cf) и хранилища конфигурации: ежедневно в 03:00
  скриптом `backup_cf.ps1` на msk-app20.

Задания выполняются планировщиком SQL Server Agent. Регламентные
задания 1С (обмен с сайтом, пересчёт итогов) на время полной копии
не останавливаются.

## 3. Хранение

- Локальное хранилище: диск `E:\Backup` на сервере СУБД, глубина 3 дня.
- Сетевое хранилище: `\\msk-nas01\backup\1c`, глубина 30 дней.
- Внешнее хранилище: объектное хранилище в облаке, глубина 12 месяцев,
  выгрузка еженедельно в ночь с субботы на воскресенье.

Копии шифруются на стороне SQL Server (Backup Encryption, AES-256).
Сертификат шифрования хранится в отдельном сейфе и в менеджере паролей
ИТ-департамента.

## 4. Контроль

4.1. Каждое утро до 09:30 дежурный администратор проверяет отчёт
задания резервного копирования в почте. Отсутствие письма
приравнивается к сбою.

4.2. Один раз в месяц (первый вторник) выполняется тестовое
восстановление базы УТ на msk-test01 из копии предыдущей ночи.
Результат фиксируется в журнале восстановления.

4.3. Признаки проблем в отчёте:
- размер полной копии отличается от предыдущей более чем на 20 %;
- время выполнения более 90 минут;
- ошибка `Msg 3201` (недоступен путь) — проверить монтирование `E:\Backup`;
- ошибка `Msg 3013` с текстом о нехватке места.

## 5. Восстановление

Целевые показатели: RPO 30 минут для критичных баз, RTO 4 часа.

Порядок:
1. Остановить публикацию базы на веб-сервере и регламентные задания.
2. Восстановить полную копию, затем цепочку журналов до нужного момента.
3. Проверить базу через `Тестирование и исправление` в конфигураторе.
4. Возобновить регламентные задания, уведомить пользователей.

## 6. Ответственные

- Администратор СУБД — задания, отчёты, восстановление.
- Дежурный администратор — ежедневный контроль.
- Руководитель ИТ — утверждение изменений регламента.
